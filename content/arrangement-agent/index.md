# FitGen 团操编排 Agent 合并模块设计

**v0.6 · 讨论稿 · 2026-11-23**

团操编排 Agent 根据用户目标、音乐结构和原子动作库规划整节课程。模块的最终产物是逐八拍的编排时间表（IR）。下游通过这份时间表确定每个八拍的边界、依次播放的素材及其时长，以及需要生成过渡动作的时段。

## 1. 这个模块接什么，交付什么

| 接口 | 当前讨论的设计 |
|---|---|
| 用户需求 | 训练目标（如增肌、燃脂）、目标肌群、身高、体重。可补充跟练经验，帮助判断新动作需要多少教学时间。课程范围统一为无器械跳操。 |
| 音乐结构化信息 | 模块一作为外部工具提供 BPM、beat、downbeat、带标签的音乐段落和八拍网格。每块保留原有 ID、起止时间、逐拍索引及完整性。 |
| 动作数据库 | `clips` 表提供原子动作的 SMPL-X 引用、动作描述、时长、倍率范围及训练标签。模块 8 提供主要锻炼肌群和原速能耗。关系图提供已标注的镜像配对和教学变式。 |
| 编排结果 | 按音乐顺序输出各八拍的起止秒数、音乐段落、教学意图和有序播放条目。每条记录一次完整动作的素材 ID 与目标时长，或一段待生成过渡的说明与预留时长。 |

服务器上的 `Module2_xtw` 已能为单段动作求时间映射。本版将它放在编排之后。下游读取 IR 和源 SMPL-X，执行动作变速、常规接缝平滑，并按 IR 中的过渡请求调用过渡动作 skill。

## 2. Agent 怎样编一节课

Agent 在内部结合用户目标、LLM 的编课先验、音乐段落、能耗和肌群标签，决定教学节奏并查询真实动作。例如主歌先教侧步，第一次副歌加入手臂，第二次副歌复现这个组合。这些决策指导查库和试排；定稿时，Agent 将选定的动作及过渡按播放顺序写入 IR。

1. **读整曲，安排教学顺序。** Agent 将用户目标与实际段长放在一起考虑，决定哪些段落适合热身、引入新动作、重复强化和放松。一首歌若开头就是副歌，仍需考虑用户第一次接触动作时的学习时间。音乐标签是规划依据，课程阶段由 Agent 结合全曲决定。
2. **结合教学进度查库。** 例如，先按主要肌群和协调难度查找容易跟练的提膝素材，读取描述与原速时长。需要换侧时沿 `mirror_id` 取已配对的素材。准备在副歌加入手臂动作时，以已教素材为目标节点，反向查找指向它的 `variation_of` 边，再按描述和难度选变式。
3. **在当前八拍内筛选完整动作。** 根据实际拍点和预留过渡确定可用时段。原子动作即使原速时长超过一个八拍，只要能在允许的播放倍率内完整放入该时段，就可以选择。如果按允许的最高倍率播放一遍仍放不下，直接跳过它，继续检查当前八拍的其他候选。同一素材可以在相邻八拍分别选用，每次都从完整周期开始。逐拍对齐交给下游 XTW。
4. **用 MotionGraph 判断接缝。** 对每一对相邻动作，MotionGraph 通过 `smplx_ref` 读取前一段末尾和后一段开头的 SMPL-X 序列，检查两端姿态和运动变化。该检查也覆盖相邻八拍之间的接缝。能常规平滑衔接时直接排入时间表；若差距明显且 Agent 决定保留组合，例如俯撑后要站立起步，则预留起身时间并写入 `transition_request`，交给下游过渡动作 skill。时间不足时改排前后动作。
5. **检查整曲，再修有冲突的八拍。** 程序校验素材 ID、动作顺序、重复次数和平均播放倍率。每块中所有动作与预留过渡的时长之和应等于块长，各条目连续、无重叠。若下游 XTW 在保持局部节奏时无法满足速度约束，或过渡生成器无法在预留时间内连接两端，回报相关八拍及原因，由 Agent 局部改排。

**提示词最值得打磨的是需要判断的地方。** 第一次出现左右交替的新动作时给多少学习时间？副歌回来时，保留脚步、增加手臂、加密重复，哪种变化更符合这次训练目标？对于以肌肉训练为重点的徒手团操，可以用动作幅度、控制节奏、组次和恢复时间组织课程。建议为同一首歌写出不同训练目标的对比例子。

## 3. 最终产物：逐八拍编排 IR（暂定 v1）

IR 使用 JSON，按整曲、八拍时间块和播放条目三层组织。每块记录模块一识别的音乐段落和 Agent 确定的教学意图。课程阶段安排、教学策略的选择依据、能耗与肌群标签、候选评分和选取理由属于内部规划信息。下游沿 `blocks[] → items[]` 顺序播放，以 `clip_id` 读取源 SMPL-X 素材。

| 对象 | 字段 | 约定 |
|---|---|---|
| 整曲 | `schema_version`、`music_grid_ref`、`blocks` | 当前格式标识为 `fitgen-arrangement-v1`。`music_grid_ref` 指向本次使用的模块一音乐网格。 |
| 时间块 | `block_id`、`start_sec`、`end_sec`、`music_sections`、`teaching_role`、`items` | 每块沿用上游块的 ID 和全曲绝对秒区间。`music_grid_ref` 和 `block_id` 共同定位逐拍拍点及块类型。`partial_head`、`partial_tail` 和 `gap` 沿用实际边界。 |
| 原子动作 | `kind: "motion"`、`clip_id`、`duration_sec` | 一条表示完整播放该素材一次，时长为目标播放秒数。若同一素材做两次，则连续写两条，各自给出时长。 |
| 过渡请求 | `kind: "transition_request"`、`duration_sec`、`instruction` | 条目所在位置和时长确定生成窗口。`instruction` 描述要完成的过渡。按整曲顺序取前后动作，即可定位两端素材，包括跨八拍的接缝。 |

**音乐段落 `music_sections`。** 程序依次读取模块一 `eight_count_grid[].section_ids` 中的 ID，从 `sections[]` 取对应的 `section_label`，将每对 `section_id` 和 `section_label` 原样写入数组。单段八拍写一项，跨段八拍按上游顺序写两项。即使相邻两段都叫 `verse`，也分别保留各自的 ID。

**教学意图 `teaching_role`。** Agent 按整个八拍的教学目的填写一个值。首次教动作或给已学脚步加入新的手臂配合时填 `"teach"`，带用户复练已教内容时填 `"repeat"`，没有明确教学或复练意图时填 JSON 的 `null`。首次教学时也可以连续做同一动作多遍，实际播放次数由 `items` 记录。

**时间校验。** 块区间使用左闭右开语义。下游从 `block.start_sec` 出发，依次累加每个条目的 `duration_sec`，得到其播放区间。每条时长必须为正，累加到最后一条时应恰好到达 `block.end_sec`。过渡占用块内时间，每个原子动作都在所属块内完整播放。

**候选倍率校验。** 编排时按单次动作检查平均播放倍率。设 $D_{\mathrm{src}}$ 为该素材完整原子动作的原速时长，$D_{\mathrm{slot}}$ 为分配给该次播放的 `duration_sec`，则

$$
r = \frac{D_{\mathrm{src}}}{D_{\mathrm{slot}}}.
$$

仅当 $r_{\min}\le r\le r_{\max}$ 时才可选用。倍率范围优先取素材已验证的值，缺省时使用项目约定的默认范围。预留过渡后，若最高倍率仍放不下一个完整动作，直接跳过该候选。下游 XTW 负责局部踩拍，按全曲网格统一采样。

**局部示例。** 以下截取 120 BPM 歌曲的两个连续八拍，ID 和时长用于演示。

```json
{
  "schema_version": "fitgen-arrangement-v1",
  "music_grid_ref": "song_001.eight.json",
  "blocks": [
    {
      "block_id": "block_004",
      "start_sec": 12.0,
      "end_sec": 16.0,
      "music_sections": [
        { "section_id": "section_01", "section_label": "verse" }
      ],
      "teaching_role": "teach",
      "items": [
        {
          "kind": "transition_request",
          "duration_sec": 2.0,
          "instruction": "从上一八拍结束时的站姿进入双手俯撑，为交替点肩做好准备"
        },
        { "kind": "motion", "clip_id": "plank_tap_02", "duration_sec": 2.0 }
      ]
    },
    {
      "block_id": "block_005",
      "start_sec": 16.0,
      "end_sec": 20.0,
      "music_sections": [
        { "section_id": "section_01", "section_label": "verse" },
        { "section_id": "section_02", "section_label": "chorus" }
      ],
      "teaching_role": "repeat",
      "items": [
        { "kind": "motion", "clip_id": "plank_tap_02", "duration_sec": 2.0 },
        { "kind": "motion", "clip_id": "plank_tap_02", "duration_sec": 2.0 }
      ]
    }
  ]
}
```

`block_004` 在 [12, 14) 秒为站姿进入俯撑预留过渡，在 [14, 16) 秒第一次教交替点肩。`block_005` 在 [16, 20) 秒跨过主歌和副歌的边界，仍沿用已教动作，连续完整播放两遍交替点肩。

## 4. 动作数据库：素材表与关系图

### 动作素材表 `clips`

一行对应一段可以完整播放一次的 SMPL-X 原子动作。IR 中的 `clip_id` 直接引用该行。

| 字段 | 含义 |
|---|---|
| `clip_id` | 素材的唯一 ID |
| `smplx_ref` | 完整 SMPL-X 动作序列的存储引用 |
| `action_name` | 标准动作名，如“单侧提膝”。同名的不同素材各自保留 ID |
| `description` | 这段素材实际完成的动作，如“右膝抬起一次，双臂同时上举，随后收回” |
| `source_duration_sec` | 原速完整播放一次的时长，单位为秒 |
| `rate_range` | 允许的播放倍率范围，用于判断一次完整播放能否放入分配的时段 |
| `primary_muscles` | 模块 8 输出的主要锻炼肌群 |
| `energy_kj` | 模块 8 估计的整段素材原速播放一次的能耗，统一为 kJ |
| `impact` | 冲击程度，取低、中、高 |
| `coordination` | 协调难度，取低、中、高 |

### 素材关系图

节点为 `clip_id`。图中保留两种边：

| 边 | 方向 | 编排用途 |
|---|---|---|
| `mirror_id` | 对称 | 读取已有的左右镜像配对，从任一端都可找到对应素材 |
| `variation_of` | 变式 → 基础动作 | 从变式可找到对应基础动作；从已教的基础动作反查，可得到用于教学进阶的变式 |

例如，`knee_raise_right` 和 `knee_raise_left` 是一对已标注的右侧、左侧提膝素材。`knee_raise_right_reach` 在右侧提膝时增加双臂上举。三段素材对应两条边：

```text
knee_raise_right       ←─ mirror_id ─→  knee_raise_left
knee_raise_right_reach ── variation_of → knee_raise_right
```

Agent 用这张图寻找换侧或教学变式。选定播放顺序后，动作之间的物理接续由 MotionGraph 根据相邻素材的 SMPL-X 边界序列判断。

## 5. 下一轮最值得一起改的地方

| 待讨论问题 | 当前建议 | 会影响什么 |
|---|---|---|
| “慢一点教会，副歌燃起来”由哪些变化表达？ | 首版区分动作速度、每八拍重复数、幅度、协调难度。优先比较“保留脚步加手臂”和“同动作加快” | 教学标签、提示词和素材库要准备的变式 |
| 能耗在选动作时有多大决定权？ | 先作为相同训练意图下的排序依据。若要限制总量或区间，再明确单位、估计条件和允许偏差。 | Agent 在内部如何筛选、排序和检查课程总量，以及何时调用模块 8 |
| 什么时候值得留出专用过渡窗口？ | 结合 MotionGraph 匹配后的差距、体位变化和可用时长，用真实动作对确定“常规平滑／预留过渡／改排”的判据 | 可保留哪些有教学价值的动作组合，以及过渡 skill 有多少生成时间 |

建议第一次评审选一首含重复副歌的歌，准备基础版、进阶版以及一对难连接的真实素材。逐段看三个现象：用户第一次见动作时能否学会，副歌回来时能否认出组合，切换时身体是否来得及到下一个起始姿态。根据实际失败的位置，再决定要补提示词、补数据库标签，还是改工具接口。
